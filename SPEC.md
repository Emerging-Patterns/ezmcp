# ezmcp specification

This is the list of every behavior ezmcp guarantees, each under a stable requirement ID. Every requirement has one of two levels. A **Proved** requirement holds for every input, and is backed by a quantified law (a `for` or `exs` binder) in `LAWS.bend` that passes the proof gate. A **Trusted** requirement is an assumption ezmcp cannot check from inside its own gate, and it is listed in the trust boundary below. A Proved requirement whose laws have not all landed has status **pending**: we intend to prove it, and until then it is not guaranteed. The proof gate is this check: the first line `bend PROOF.bend` prints is exactly `ALL PROOFS CHECK`. Tests and fixtures are never evidence for a requirement.

## Source

ezmcp speaks three revisions of the Model Context Protocol: **2025-03-26**, **2025-06-18** and **2025-11-25**. Every row comes from a normative statement of one of them, or of JSON-RPC 2.0, which MCP builds on. A row cites its section and quotes the requirement (MUST, MUST NOT, SHOULD, MAY), then says what ezmcp does about it. Sections are cited by their path under <https://modelcontextprotocol.io/specification/>: a path that starts with a revision, as `2025-03-26/basic/lifecycle#initialization`, is that revision's page and anchor, and a bare path, as `basic/lifecycle#initialization`, is 2025-06-18's, whose words for that requirement 2025-03-26 and 2025-11-25 share unless the row cites theirs. `schema.json` is 2025-06-18's schema, <https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-06-18/schema.json>, and `JSON-RPC §N` is a section of <https://www.jsonrpc.org/specification>. Every requirement these revisions state for a feature ezmcp does not implement is listed under [Not implemented](#not-implemented), with its section, so what ezmcp does not do is as plain as what it does.

What differs between the three for the tools-only, stateless subset ezmcp serves is small, and each difference is a row: 2025-03-26 receives JSON-RPC batches (MCP-RPC-12, MCP-HTTP-9) and has no `structuredContent` (MCP-TOOL-7); 2025-06-18 adds the `MCP-Protocol-Version` header (MCP-HTTP-6, MCP-HTTP-8); 2025-11-25 names the 403 for a refused `Origin` (MCP-HTTP-5). A message is read by a revision: over HTTP the one its `MCP-Protocol-Version` names, or 2025-03-26 when it names none (MCP-HTTP-8); over stdio the one the server answered the stream's last `initialize` with, and the latest before any (MCP-LIFE-5).

The requirements are about the pure modules: `src/rpc.bend` (JSON-RPC messages), `src/server.bend` (a server's answers), `src/web.bend` (the streamable HTTP transport's decisions), `src/line.bend` (the stdio transport's decisions), `src/sse.bend` and `src/client.bend` (the client side). They do no IO, so `LAWS.bend` and `PROOF.bend` import them and nothing else. `src/io.bend` runs the effects on ezhttp and Base and acts on those modules' answers (MCP-TRUST-1). It holds the one effect of ezmcp's own, a read of stdin (MCP-TRUST-5). `main.bend` names them: each of its pure names is a module's function and no more, so it carries no law of its own: bolt's `coverage` rule, an error in `bolt.bend`, flags the undotted ones, and each carries a `# noqa: L001` naming the function it re-exports.

One deliberate departure from `schema.json`: its `JSONRPCError` requires an `id` that is a string or an integer, but JSON-RPC §5 requires `"id": null` in the error for a message whose id could not be read (a parse error, or an invalid request with no valid id). ezmcp follows JSON-RPC there (MCP-RPC-2, MCP-RPC-9, MCP-RPC-10), as MCP's own SDKs do; `basic/transports#sending-messages-to-the-server` allows such an error "that has no `id`" in an HTTP 400 body.

## Format

A requirement table is any table whose header row is exactly `| ID | Requirement | Level | Status | Law |`. An ID is uppercase segments joined by hyphens, at least two (`[A-Z][A-Z0-9]*(-[A-Z0-9]+)+`), unique within the requirement tables, and never reused once released. Level is `Proved` or `Trusted`. Status is `proved` or `pending` for a Proved row and empty for a Trusted row. A Law cell holds `<path> <law>` entries, paths relative to this file, separated by `; `. A proved row names one or more laws, and together they prove it. A pending row may name laws that each prove part of it; the row stays pending until its requirement is proved in full, and "Left to prove" says what is missing.

A law proves a requirement when a comment line `# <ID>`, alone on its line, sits in the unbroken comment block directly above its `law` line. A law may carry several tags, one per line:

```
# LAW: a notification gets nothing back
# MCP-RPC-3
law tell_is_quiet:
```

A tag may name a proved or a pending requirement, never a Trusted one or an ID no requirement table lists. bolt's `trace` rule checks all of this over the whole tree, and its `closed` rule rejects a law with no binder; both are errors in `bolt.bend`.

## Requirements

`basic/transports#streamable-http`, which 2025-03-26 introduced and 2025-11-25 keeps. `Web.decide` takes one HTTP request (as ezhttp parses it) to a server's MCP endpoint and decides the reply, or a tool call or a batch to run first. Every reply is a single response with a body; ezmcp never opens an SSE stream and never issues a session.

### stdio (MCP-STDIO)

`basic/transports#stdio`. stdin is read as bytes, a chunk at a time; `Line.cut` splits what has been read into whole lines and a rest, which waits for the next chunk; each whole line is decoded from UTF-8 and is one message. When stdin ends, the rest is the last message.

| ID | Requirement | Level | Status | Law |
| :---- | :---- | :---- | :---- | :---- |
| MCP-STDIO-1 | `basic/transports#stdio`: "Messages are delimited by newlines, and **MUST NOT** contain embedded newlines." For every buffer, the cut's lines and rest are the buffer's bytes in order; every line it hands on ends with its newline and holds no other; and the rest it keeps holds no newline. So every message is exactly the bytes between two newlines | Proved | proved | LAWS.bend split_flat; LAWS.bend split_pieces; LAWS.bend cut_glue; LAWS.bend cut_lines; LAWS.bend cut_rest |
| MCP-STDIO-2 | `basic/transports`: "JSON-RPC messages **MUST** be UTF-8 encoded." ## Trust boundary

| ID | Assumption | Why it is trusted |
| :---- | :---- | :---- |
| MCP-TRUST-1 | `src/io.bend` acts on the pure modules' answers in order, as the requirement states, and runs the runner exactly for a tool call. | It is IO sequencing: effects are foreign, so the checker cannot run an IO program and no law can state what happens after an effect. Every decision it acts on is one of the Proved rows above. |
| MCP-TRUST-2 | ezhttp's server and client behave as its SPEC.md states, and the connection steps its serve loops are built of behave the same when ezmcp's context-carrying loops call them. | It is another package, pinned in `ez.lock.toml`, whose socket effects are foreign C and JS that no law here reaches. |
| MCP-TRUST-3 | ezjson's parser and printer behave as its SPEC.md states. | It is another package, pinned in `ez.lock.toml`; its rows are proved in its own gate, which this gate does not re-run. |
| MCP-TRUST-4 | The runner validates its inputs and answers a tool result or a protocol error. | It is the caller's code, which ezmcp does not see. |
| MCP-TRUST-5 | `ezmcp.stdin` reads file descriptor 0, and Base's print effects write stdout and stderr, as the requirement states. | They are foreign C and JS: ezmcp's own (`src/effs/stdin.c`, `src/effs/stdin.js`) over `read(2)`, and Bend's runtime (`effs/write.c`, `effs/print_err.c`), which no law reaches.
